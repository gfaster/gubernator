# Jobs


A Job is a program run by a gubernator client. By default, jobs are intended to
be somewhat lighter-weight, so we don't use virtual machines or heavy
namespacing (containerization) by default.

When a client wishes to start a Job, they send a Job Request to the Gubernator.
A Job Request is a XML document detailing how to select a host, and how to run
the job on each host.


## Job Requests

A Job Request has two components, the machine selection and the Job definition.
The Job definition is modular to allow changes based on the selected machine(s).

Machine selection is encoded as a simple DSL to query properties of a machine.

```xml
<machine_sel>
    <predicate>
        <!-- exactly one of these must be true -->
        <one_of>
            <arch name="x86_64" />
            <arch name="arm64" />
        </one_of>
    </predicate>

    <predicate>
        <!-- one or more of these must be true -->
        <any_of>
            <!-- all of these must be true -->
            <all_of>
                <os name="debian" />
                <package name="curl" />
                <package name="gcc-14" />
            </all_of>

            <!-- all of these must be true -->
            <all_of>
                <os name="freebsd" />
                <package name="curl" />
                <package name="gcc-14_5" />
            </all_of>
        </any_of>
    </predicate>

    <!-- all predicate nodes and logical connectives can be made optional,
    though they'll still be evalulated if there are potential explanations -->
    <predicate fail="ignore">
        <implication>
            <antecedent>
                <os kernel="linux" />
            </antecedent>
            <consequent>
                <!-- lazily evalulated, we won't get an explanation on FreeBSD -->
                <!-- TODO: what's the format of an explanation? -->
                <one_of fail="explain">
                    <os version="6.12" />
                    <os version="6.13" />
                    <os version="6.14" />
                </one_of>
            </consequent>
        </implication>
    </predicate>

    <!-- I considered making memory a predicate for more flexibility, but the
    semantics for it would be unintuitive. Maybe it's worth doing anyway -->
    <memory>
        <!-- amount kept in RAM and reserved exclusively -->
        <!-- to improve clarity, base-10 units (KB, MB, etc) are not accepted -->
        <min>1GiB</min>
        <!-- amount potentially shared, must be greater than or equal to min -->
        <peak>2GiB</peak>
        <!-- amount of the peak memory that can be swapped, will never swap
        (but might be killed) if usage is less than peak - swappable -->
        <swappable>250MiB</swappable>
    </memory>

    <!-- run on at most 3 different machines -->
    <limit>3</limit>
</machine_sel>
```


## Job description

We'll fully utilize XML as a markup language here (eventually). I'll be loosly
basing it on `systemd.unit(5)`/`systemd.service(5)`.

In the interest of maximizing usability with minimal admin permissions, we'll
try to use commonly installed utilities to provide necessary components. For
example, a build system will make it's results availiable as artifacts, served
over 9p. If no virtualized filesystems are availiable, then future jobs wanting
to make use of it will have to just manually copy it over with userspace 9p.
Alternatively, if availiable, it can be mounted through FUSE, or if we have the
relevant capabilities, v9fs.

This requires the capacity to specify the qualities we expect of artifacts. Do
they need to be downloaded in full? Do they need to be made availiable for a
long time? Are they big enough that we just want to keep them on their original
block device?

```xml
<job_desc>
    <type>exec</type>

    <exec_start>
        <exec>cargo</exec>
        <arg>build</arg>
        <arg>--release</arg>
    </exec_start>

    <working_dir>
        <!-- create new temporary directory -->
        <temp />

        <!-- set up files in the working directory, all paths are relative to the working dir -->
        <!-- in the future I want better ways to do this (9p? NFS? block devices?), but this is a start -->
        <contents>
            <dir name="src" src="sftp://git-host:my-project/src" />

            <!-- Use subresource integrity hashes -->
            <file
                name="Cargo.toml"
                src="sftp://git-host:my-project/Cargo.toml"
                integrity="sha256-c56581c86c399df804ec64116b71cdb2bb293748c2049acde96b9dc1f376ed19" />

            <!-- I've added spaces here for display but this is the literal contents -->
            <file name="Cargo.lock">
                # This file is automatically @generated by Cargo.
                # It is not intended for manual editing.
                version = 4
                ...
            </file>
            <file name="script.sh" perms="0544" encoding="base64">
                IyEvdXNyL2Jpbi9lbnYgYmFzaAplY2hvICdvb29oIGEgcGllY2Ugb2YgY2FuZHknCg==
            </file>
        </contents>

        <!-- keep files and serve them to the requester or make availiable to future runs over 9p -->
        <!-- this has not been thought out at all and will probably change entirely -->
        <keep>
            <!-- keep target/release around for at least one hour. The daemon will provide a 9p socket -->
            <dir path="target/release" duration="1h" />
        </keep>
    </working_dir>

    <!-- corresponds to TimeoutStartSec -->
    <start_timeout>60s</start_timeout>
</job_desc>
```

```xml
<job_desc>
    <remain_after_exit />

    <type>oneshot</type>

    <exec_start>
        <exec>/usr/bin/myservicectl</exec>
        <arg0>myservicectl</arg0> <!-- optional, defaults to exec -->
        <arg>start</arg>
    </exec_start>

    <exec_stop>
        <exec>/usr/bin/myservicectl</exec>
        <arg>stop</arg>
    </exec_stop>

    <working_dir><home /></working_dir>

</job_desc>
```
